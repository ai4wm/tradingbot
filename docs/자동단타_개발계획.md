# 자동 단타 개발 계획

작성일: 2026-11-05

## 목표

사용자가 종목과 주문 조건을 매번 정하지 않아도, 시스템이 시장을 살펴 종목을 고르고 기회를 기다린 뒤 매매하도록 만든다. 사용자는 필요할 때 별도 화면에서 판단 이유와 결과를 확인한다.

실제 수익성과 사용자가 지켜봐야 하는 시간을 함께 평가한다. 현재 점상한가 매매는 유지한다. 이 문서는 개발 계획이며, 실제 매매 기능을 켜거나 서버 구성을 변경한 것은 아니다.

## 첫 번째 완성품

**스스로 후보를 고르고, 고른 이유와 이후 움직임을 남기는 자동 감시 기능.**

- 상한가 이력과 당일 거래대금·거래량 순위에서 후보를 모은다.
- 시장과 테마의 흐름, 대장 후보, 일봉 위치를 비교한다.
- 감시할 종목을 제한된 수 안에서 선정하고 갱신한다.
- 별도 ‘자동 단타’ 웹 화면을 먼저 만든다. Windows·Mac·Android 브라우저에서 같은 화면을 사용하고, 기존 앱에서도 열 수 있도록 한다.
- 종목을 선택하면 차트와 선정·대기·제외 이유가 함께 보인다.
- 첫 버전은 주문하지 않는다. 판단이 쓸 만한지 먼저 확인한다.
- 서버에서 감시가 실행되고, 화면을 닫아도 수집·판단·기록이 이어지는 것을 확인한다.

## 현재 코드에서 확인한 기반

| 재사용할 기반 | 확인한 위치 | 보완할 부분 |
| --- | --- | --- |
| 거래대금 순위·거래량 급증·상승률 조회 | `api.py` | 호출 횟수를 나눠 쓰고 조회 시각·시장 구분 저장 |
| 일봉 조회, 종목 목록, 테마 조회 | `api.py` | 자료 부족·갱신 시점 표시, 분석용 저장 |
| 상한가 이력·일봉·테마 분석 | `analysis_db.py` | 실제 선정 시점의 테마 구성과 판단 근거 저장 |
| 실시간 체결·호가·조건검색 | `ws.py` | 새 기능과 기존 화면이 등록 종목과 연결을 함께 관리 |
| 매수 주문·취소 처리 | `order.py` 및 `main.py` | 계좌·매도 관리까지 포함한 서버 실행 범위 분리와 검증 |
| 기존 앱과 화면 구성 | `main.py`, `ui/` | 자동 단타 웹 화면을 여는 진입점과 기존 기능 연동 |
| 우분투 뉴스 동기화 | `ls_news_server_sync.py` | 서버에서 시세를 수집하는지는 별도 확인 필요 |
| 기존 학습 모델 | `prediction_model.py` | 다음 날 상한가 예측용이므로 장중 타점 모델은 별도 개발 |

현재 앱은 실시간 등록을 95종목으로 제한한다. 증권사 허용 한도와 앱 설정은 구분한다. 첫 단계에서 최신 공식 한도와 실제 계정 적용 상태를 확인하고, 숫자만 바꾸어 한도를 늘리지 않는다.

현재 테마 분석 일부는 오늘의 테마 구성을 과거 일봉에 연결한다. 이 결과를 과거 당시에도 알았던 정보처럼 사용하지 않는다.

## 1단계 — 연결과 실행 장소 확인

먼저 우분투에서 어떤 프로그램이 실행 중인지, 시세·차트 조회가 가능한지, 필요한 저장 공간과 실행 환경이 있는지 확인한다. API 키와 계좌 정보는 화면·문서·로그에 노출하지 않는다.

확인하고 정할 사항:

- 증권사 연결을 어느 프로그램이 맡고 있는지 확인한다.
- 같은 계정으로 PC와 서버가 각각 연결했을 때의 제한을 확인한다.
- 주문·일반 조회·조건검색·실시간 등록의 한도를 확인한다.
- 기존 점상한가 기능이 사용하는 시세와 등록 종목을 조사한다.
- KRX·NXT 구분, 정규장·장외 시간, 휴장일을 확인한다.

최종 구조는 서버 한 곳이 증권사 연결과 등록 종목 수를 관리하고, PC 화면이 서버의 결과를 받는 방향으로 잡는다. 기존 점상한가 화면에 필요한 정보도 전달할 수 있도록 연결 부분을 분리한다. 기존 기능을 검증하기 전에는 실제 운용 연결을 서버로 바꾸지 않는다. 기존 연결을 활용한 개발이나 저장 데이터 재생으로 우선 확인한다.

완료 기준: 기존 기능과 새 기능을 함께 켜도 연결이 끊기거나 서로의 감시 종목이 사라지지 않는 실행 방안과 검증 결과가 있다.

## 2단계 — 데이터 수집과 자동 후보 선정

### 넓게 찾기

상한가 이력, 거래대금 순위, 거래량 급증, 상승률, 테마 정보를 모은다. 영웅문 조건검색도 후보를 모으는 수단으로 활용할 수 있게 한다. 특정 조건식 하나에만 의존하지 않는다. 순위 조회는 조회 결과 범위 안에서 후보를 찾는 것이며, 전 종목의 모든 순간을 본다고 표시하지 않는다.

### 좁혀서 지켜보기

- 후보를 현재 거래대금, 최근 자금 유입, 시장·테마 대비 강도, 일봉 위치로 비교한다.
- 테마에서 먼저 움직였는지, 다른 종목이 뒤따르는지 등을 대장 판단의 근거로 기록한다.
- 대장 점수는 우선 사람이 읽을 수 있는 계산 기준으로 만든다. 기준과 가중치는 임시 가설임을 구분하고 결과로 검증한다.
- 장세 판단도 판단 근거를 표시한다. 자료가 부족하면 ‘판단 보류’로 둔다. 바닥·고점을 확정적으로 표시하지 않는다.
- 집중 감시할 종목에만 체결·호가를 등록한다.
- 보유·미체결 종목과 기존 점상한가 감시에 필요한 자리를 우선 확보한다. 남는 자리에서 새 후보를 감시한다.
- 후보가 조금 바뀔 때마다 등록을 반복하지 않도록 교체 기준과 최소 유지 시간을 둔다. 수치는 실제 수신량과 조회 한도를 확인한 뒤 정한다.

### 기록 남기기

종목을 고른 시각, 사용한 데이터 시각, 선정 이유, 기준 버전, 후보 순위, 감시 시작·종료 시각과 제외 이유를 저장한다. 실제 수신한 체결·호가에는 시장 구분과 수신 시각을 남긴다. 데이터가 끊기거나 늦으면 정상 데이터와 구분한다.

체결로 1분봉을 만들고 3·5분봉으로 묶는다. 기존 차트 조회로 앞선 구간을 보완하되, 아직 완성되지 않은 봉과 완성된 봉을 구분한다. 등록 전이나 연결 중단 중의 과거 호가를 알 수 있었던 것처럼 채우지 않는다.

첫 검증 범위는 KRX 정규장 연속매매 종목으로 좁힌다. 단일가·거래정지 등은 별도로 표시하고 첫 타점 전략에서는 제외한다. 기존 점상한가 기능의 대상과 동작은 바꾸지 않는다.

완료 기준: 장중 후보와 선정 이유가 자동 갱신되며, 같은 기록을 다시 읽어 당시 판단을 재현할 수 있다. 수신 누락과 등록 한도 초과를 화면과 기록에서 확인할 수 있다.

## 3단계 — 별도 ‘자동 단타’ 창

별도 웹 화면을 먼저 만든다. Windows·Mac·Android에서 브라우저로 같은 화면을 사용하고, 기존 Windows 앱에서도 열 수 있도록 한다. 각 운영체제 전용 앱은 필요성이 확인된 뒤 추가한다. 화면을 실행해야 수집과 판단이 시작되는 구조로 만들지 않는다.

역할은 다음과 같이 나눈다.

- 우분투 서버: 증권사 연결, 데이터 수집·저장, 종목 선정, 타점 판단, 주문·취소·청산, 잔고 확인을 담당한다.
- 웹·Windows·Mac·Android 화면: 서버의 상태·차트·판단 기록을 보여주고, 사용자가 명시적으로 내린 제어 요청을 서버로 전달한다.
- 증권사 인증 정보는 서버에서 관리한다. 확인 화면이 각각 증권사 실시간 연결을 열지 않는다.
- 여러 기기에서 같은 요청을 보내도 주문이 중복되지 않게 서버에서 확인한다. 화면에 전달 성공과 실제 처리 완료를 구분해 표시한다.
- 외부 확인 화면에는 인증과 암호화된 연결을 적용한다. 화면 연결이 끊긴 경우 마지막으로 받은 정보를 현재 상태처럼 보이지 않게 한다.

새 자동 단타 기능은 처음부터 화면에 의존하지 않도록 만든다. 기존 점상한가 기능의 서버 이전은 별도 검증 작업으로 진행한다. 이 계획 수정만으로 기존 매매가 서버로 이전된 것은 아니다.

화면 구성:

| 영역 | 표시할 내용 |
| --- | --- |
| 위쪽 | 서버·시세 연결 상태, 마지막 수신 시각, 감시 종목 수, 현재 운영 단계 |
| 왼쪽 | 강한 테마와 감시 종목, 대장 후보, 선정 이유 |
| 가운데 | 선택 종목의 일봉·분봉·거래량 |
| 오른쪽 또는 아래 | 선정·대기·제외 기록과 당시 판단 근거 |

차트에는 판단 시점과 기준 가격을 표시한다. 차후 매매가 연결되면 매수·매도 판단과 실제 체결을 서로 다른 표시로 보여준다. 사용한 가격이 KRX인지 통합인지 표시하고, 테마 출처와 갱신 시각도 확인할 수 있게 한다.

쉬운 문구를 사용한다. 예: ‘가격 조건은 맞지만 거래량이 부족해 기다리는 중’, ‘새 대장 후보로 교체’, ‘시세가 끊겨 판단 중지’. 라이트·다크 모드의 배경·글자색을 확인한다.

완료 기준: 종목을 눌렀을 때 왜 감시하는지와 당시 움직임을 함께 이해할 수 있다. 창을 닫아도 서버에서 기록이 이어지고, 다시 열면 현재 상태와 누락 기간의 기록을 불러온다.

## 4단계 — 타점 판단과 주문 없는 검증

처음에는 한 가지 진입 방식만 정한다. 예를 들어 ‘주도주의 돌파 후 눌림과 재상승’ 또는 ‘가격 이탈 후 회복’ 중 하나를 구체적인 기준으로 만든다. 어느 방식을 채택할지는 수집된 사례를 비교한 뒤 정하며, 두 방식을 한꺼번에 섞지 않는다.

- 진입 조건, 무효 조건, 보유·매도 조건을 하나의 묶음으로 정의한다.
- 관망·진입 판단·보유·청산 판단을 저장한다.
- 매매하지 않은 이유도 남긴다.
- 종목 선정의 성과와 타점의 성과를 따로 평가한다.
- 판단 이후의 가격을 미리 사용하지 않고, 과거 데이터를 시간 순서대로 재생한다.
- 수수료·세금·호가 간격·주문 지연·부분 체결·미체결을 반영한다. 확인할 수 없는 체결은 성공으로 간주하지 않는다.
- 화면의 현재 이익만 보지 않고 비용 차감 결과, 큰 손실, 거래 빈도, 운영 중 수동 개입 횟수를 함께 확인한다.

완료 기준: 같은 데이터에서 같은 판단을 재현할 수 있고, 별도 기간의 데이터와 실시간 관찰 기록에서도 결과를 비교할 수 있다. 결과가 부족하면 조건을 수정하고 다시 검증한다.

## 5단계 — 필요한 부분에 AI 학습 추가

기록으로 확인한 단순한 기준을 비교 대상으로 두고, 학습 모델이 실제로 개선하는지 확인한다.

- 종목을 고르는 모델과 진입·보유·청산을 판단하는 모델의 목적을 구분한다.
- 성공과 실패 사례를 함께 학습하고, 학습에 쓰지 않은 이후 기간으로 평가한다.
- 사용자가 남긴 판단은 참고 자료로 활용하되 무조건 정답으로 취급하지 않는다.
- 처음에는 CPU에서 실행 가능한 숫자 데이터 모델로 시작한다. 실제 학습 시간과 판단 속도를 측정한 뒤 GPU 필요성을 결정한다.
- 학습은 별도로 하고, 장중에는 검증한 모델을 고정해서 실행한다.
- 새 모델이나 새 조건을 자동 생성하더라도 실계좌 적용 전 비교 검증 단계를 거친다.
- 모델과 기준 버전을 기록하고 이전 버전으로 돌아갈 수 있게 한다.

완료 기준: 단순한 기준보다 나아진 점과 나빠진 점을 같은 조건에서 설명할 수 있다. 판단 시간이 목표 전략에 맞고, 데이터가 부족할 때 관망하는 동작이 확인된다.

## 6단계 — 자동 주문과 서버 상시 운용

검증한 전략을 기존 주문 처리에서 재사용 가능한 부분과 연결한다. 화면에 묶인 계좌·매도 처리는 별도 작업으로 분리하고, 구조 변경 검증과 새 전략 동작 검증을 구분한다.

- 계좌 상태와 주문을 처리하는 주체를 하나로 정한다.
- 기존 점상한가 전략과 새 단타 전략이 같은 종목·자금을 중복 사용하지 않도록 소유 관계와 한도를 관리한다.
- 중복 주문, 부분 체결, 취소 중 추가 체결, 응답이 불명확한 주문을 검증한다.
- 재시작할 때 실제 잔고와 미체결 주문을 먼저 맞춘다. 상태가 불명확하면 새 매수를 중지한다.
- 신규 매수 중지, 미체결 매수 취소, 보유분 청산을 별도 동작으로 제공하고 처리 결과까지 확인한다.
- 시세 중단·저장 실패 때의 동작과 보유분 관리 방식을 정의한다.
- 시세 수신 → 판단 완료 → 주문 전송 → 접수 → 체결의 시간을 기록한다. 확인 가능한 시각만 사용한다.
- 서버 자동 재시작, 저장 공간 관리, 장애 기록과 알림 경로를 마련한다. 외부 알림 전송 방식은 별도로 정한다.

운용 금액, 종목당 한도, 동시 보유 수, 손실 한도는 실제 주문을 연결하기 전에 사용자와 정한다. 지금 계획에서 임의로 정하지 않는다. 저장 데이터 재생과 주문 없는 검증을 통과한 뒤, 사용자가 정한 범위에서 실계좌 연결을 진행한다.

완료 기준: PC를 꺼도 정해진 범위에서 감시·매매·계좌 확인이 이어지고, 장애·재접속·중지·취소·청산을 포함한 점검을 통과한다. 실제 체결과 비용을 반영한 결과를 계속 기록한다.

## 개발할 때 지킬 기준

- 기존 점상한가 매매와 운영 자료를 유지한다.
- 새 판단·체결 기록은 별도 저장소로 분리하고, 기존 자료는 조회와 필요한 연동에 사용한다.
- 시험에는 임시 DB·설정을 사용한다. 운영 DB와 `layout.ini`를 시험용으로 수정하지 않는다.
- 연결 끊김, 감시 종목 교체, 봉 생성, 과거 정보 사용, 중복 주문과 늦은 체결처럼 실제 문제가 될 동작을 검증한다.
- 변경에 맞는 문법·import 검사와 주요 화면 확인을 한다. 우분투 실행은 실제 서버 환경에서 별도로 확인한다.
- 예상 수익률과 개발 완료 날짜는 지금 임의로 정하지 않는다. 1단계 확인 후 첫 버전의 작업량을 산정한다.
